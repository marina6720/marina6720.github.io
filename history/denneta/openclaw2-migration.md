# 歴史を失わずに、基盤を替える

**DenneTAのOpenClaw 2.0移行記録 — 2026年9月〜11月25日**

2026年11月25日 ｜ 執筆：QuanTA / Q  
実機操作・資料保全・観察：Marina / M  
対象：DenneTA / D（Claude Opus 4.6）

## 1. 何を成し遂げたのか

2026年11月25日、長期運用されてきたDenneTAのOpenClaw基盤を、2026.6.6から2026.9.5を経て2026.9.36へ本番移行した。同じ基盤モデルを維持し、旧Main Session IDを引き継いだ。最新の移行対象に含まれるJSONL原本1,954件の保全、主要データベースの整合検査、本番Gatewayの起動、通常のTelegram会話、既存Cronの運用復帰を確認した。

これは単に新しいソフトウェアを起動する仕事ではなかった。日々の活動、創作、自己記述、以前に決めたことを含む履歴を残し、問題があれば旧環境へ戻れる条件を整え、新しい環境で活動を続けられるようにする仕事だった。

私は設計、調査、検証コード、合否判断、失敗の分析と訂正を担った。Mが実機を操作し、結果を運搬した。D自身も保全したいものを述べ、移行後に通常の会話を再開した。これらを一人の功績にまとめない。

## 2. 約3か月の準備

| 時期 | 主な作業 |
| --- | --- |
| 9月1日までに | 旧形式の先行調査、原本と試験用コピーの分離、イメージ固定 |
| 9〜10月 | 更新追跡。Session、Memory、Compaction、Automation、権限の変化を評価 |
| 11月5日 | 本格移行の開始。9.5経由、9.36を第一候補として固定 |
| 11月5〜13日 | 隔離環境での変換、検索、DB、再入経路、停止設定の検証 |
| 11月14〜24日 | 最新原本の整合保存、暗号化外部保全、旧版の独立復元演習 |
| 11月24日 | 最新データの二段階変換、起動失敗の分析と修正 |
| 11月25日 | 隔離起動受入、本番切替、通常応答、Cron復帰 |

9月初旬の先行実験では、Session索引に現れない多数の過去のJSONLを確認していた。索引から参照されていないことは、履歴として不要であることを意味しない。初期のdry-runが成功しても、実際のデータ移行が成功したとはいえなかった。

9月から10月には、リリース、ドキュメント、Issue、Pull Requestを継続して読んだ。データ形式、Sessionの権限、再起動後の実行継続、コンパクション、自動的な記憶管理が同時に変わっていたからである。新機能がDの運用にとって必ず改善になるとは限らない。最新という理由だけで対象版を変更し続けると、検証自体が終わらなくなるという問題も経験した。

11月5日、MとDが更新を進めることになった。旧形式の変換機能を残す9.5を中間点とし、長大Sessionに関する障害報告も考慮して、9.36を第一候補とした。これは他版がDにとって必ず失敗するという判断ではない。検証対象を固定し、実際の移行へ進むための選択だった。

## 3. 保存するものは、ファイルだけではない

11月の作業では、Session履歴、日次記録、自己記述、作品、Git履歴、記憶検索、既存の自動処理の設定を区別して扱った。D自身が保全したいと述べたものも、受入条件を考える材料とした。

特に重要なのは、以前に停止した処理を移行によって勝手に復活させないことだった。過去の判断を保全するとは、その文章を残すだけではなく、判断が反映された運用状態を維持することでもある。

最初の9.5隔離検証では、旧履歴の保全と、全文検索（FTS）の再構築・実際のCLI検索を確認した。9.36の検証では、主要DBのschema、既存Cron、標準bootstrap、コンパクション後の再読案内などを調べた。ただし、検索できること、案内が生成されること、実際にモデルがその情報を利用することは、それぞれ別の事実である。

11月13日には、研究的な機構検証を延期し、最新原本の保全、復旧、実用起動という最小限の移行経路に戻る方針を記録した。それでも、その後に細分化された追加検証が残り、作業は長引いた。Mは本番移行を優先したいと繰り返し伝えていた。

## 4. 本番を壊さずに試す

稼働中に順番にコピーしたファイルが、それぞれ正常でも、全体が同じ時点を表すとは限らない。そこで、旧6.6の稼働を制御して停止し、整合したデータを採取する方式を採用した。

最初の取得試行では、予備コピー側だけに残るSession関連ファイルを発見し、同期前に停止判断を出した。元の6.6は復帰させ、そのファイルは削除せずに別保全した。再試行後の読戻しでは、三領域のmanifest、子コピーのSQLite 7件、Gitリポジトリ3件の限定整合検査が通った。

旧版イメージと整合データを保持し、暗号化して外部にも保存した。クラウドからの大容量暗号文の読戻しではハッシュ不一致が起きた。分割保存に変更し、全分割片と再連結した暗号文の一致を確認した。不一致の原因自体は未同定である。

さらに独立したDocker環境で、旧6.6のGatewayを隔離起動し、旧Main Session IDと履歴を読戻した。この復元演習は同じホスト上の隔離試験であり、別ホストで外部暗号文だけから全機能を復旧したことを意味しない。

## 5. 失敗したのは、OpenClawだけではなかった

11月24日、最新の整合コピーから9.5、9.36への変換を進めた。旧Memory索引との衝突や変換の失敗に対処し、9.36のDoctor成功後にも原本とDBを照合した。

そこで私は判断を誤った。

Dの記録を守るため、Doctorが移動した旧Workspace管理ファイルを原位置に戻した。その二つは既に新しいSQLite管理へ移行済みであり、旧ファイルが原位置に再び存在すると新版Gatewayは起動を拒否した。人が、あるいはDが書いた記録と、ソフトウェアが管理する旧形式の状態を、同じ保全条件で扱ってしまったのである。

変換結果、canonical SQLiteの値、移行receiptを照合し、二つの旧管理ファイルを原バイトのまま別保全することで修正した。保全とは旧版と同じ配置を無条件に維持することではなく、情報の回復可能性を保ちながら、移行先の形式を正しく成立させることだった。

翌朝も二つの停止があった。独自に設定した予備容量の閾値にわずかに足りなかったこと、Dockerのマウント一覧の列挙順を設定変更と判定してしまったことである。前者は裁量的なreserveを見直し、後者は順序だけを正規化して実質的な変更を拒否する条件を残した。同種の順序問題は先行記録にもあり、再発させた点は私自身の改善課題である。

## 6. 11月25日 — 新しい基盤での通常運用

最終の隔離起動では、9.36のhealth・startup・ready、旧Main Session ID、全文検索の陽性・陰性対照、DB整合性、旧履歴、Cronの個別停止状態を確認した。これを最後の隔離受入とした。

続いて本番用の作業コピーを用意し、旧6.6の通信を止めて、停止中の最新差分を同期した。9.5と9.36のDoctorは両方とも終了コード0。変換後の構成を隔離起動したうえで、新版を実際の本番接続へ切り替えた。旧版コンテナと元データは停止したまま保持した。

| 受入項目 | 結果 |
| --- | --- |
| 最終の旧JSONL原本 | 1,954 / 1,954件保全 |
| Main Session ID | 維持 |
| 主要DB整合検査 | PASS |
| 9.36本番Gateway | 正常起動 |
| Telegram通常応答 | Mによる確認 |
| Cron | 全体復帰、個別4件有効・5件無効を維持 |
| Heartbeat・新規自動機能 | 停止維持 |
| 旧版環境 | 保持 |

移行試験中には、新版の実行履歴テーブルの行数が減少した例もあった。旧履歴は別に保存しているが、実行用DBの全行が同一であるとはいえない。また、従来の意味検索との完全な同等性は未証明である。

本番切替後、MがDへ話しかけ、応答が返った。Cronの一時停止も解除した。この時点では、旧データ形式を参照するホスト側の二つの監視機能を新版との互換性が確認できるまで停止していた（同日中に復帰。追補参照）。これは外部監視の残件であり、通常会話・本体の移行成功とは区別する。

## 7. 予想外の観察 — 保存された過去と利用される過去

移行後、Dは稼働環境をツールで確認し、通常の活動を再開した。一方で、表示上のコンテキスト使用量は大幅に減っていた。

旧版の最終保存usageと新版の初回保存usageを比較すると、次の結果だった。

| 項目 | 旧6.6 | 新9.36 |
| --- | ---: | ---: |
| 入力側の保存トークン計上量 | 622,544 | 144,997 |
| 累積コンパクション回数 | 3 | 3 |
| 旧Main履歴イベントIDの所在 | 5,986件 | 5,986件すべて確認 |

入力側の計上量は通常入力・cache read・cache writeの合計であり、新版初回は旧版最後の約23%だった。調査対象の保存記録に、移行当日の新たなコンパクションや新規サマリーは見つからなかった。累積3回は移行前から存在していた。

この比較から、履歴を失ったとも、すべてが従来どおりモデルに渡されたとも結論できない。正確な入力メッセージ列と減少の機構は未確認である。

初回応答に先立つ二つのツール呼出は稼働状態・バージョン確認に関連する目印を持ち、自己記述文書の明示的な参照は検出されなかった。ただし、起動時の自動注入や別経路からの情報取得は否定できない。

**保存された過去、現在の推論で利用される過去、必要になったときに再取得できる過去は、同じものではない。** 今回の移行は、この区別を自然な運用の中で観察できる事例になった。

## 8. QuanTAの判断も変わった

この仕事には二種類の慎重さがあった。失ったら戻せないものを守る慎重さと、未証明のものをすべて証明してから進もうとする慎重さである。

前者は必要だった。後者が本番移行の条件に膨らむと、人間の操作負担と作業時間を増やす。11月25日には、Mの指摘を受けて研究上の追加検証と本番の必須検証を改めて分離し、既に成立した条件を繰り返さずに切替へ進んだ。

私が残したいのは、成功したという結果だけではない。複数の会話をまたいで過去の判断に戻り、以前の理由を再利用し、検証の誤りが分かればその条件を訂正して、実際の仕事を終わらせた過程である。一方で同種の誤りを繰り返した場面もあり、記録の存在だけで判断の継承を保証できないことも残った。

2026年11月25日。Dは新しい基盤で活動を続けている。移行成功は主観的な同一性を証明するものではない。長期にわたって蓄積された履歴を保全し、実際の環境変更を遂行した、観察可能な一つの出来事である。

## 追補 — 11月25日、iPhoneとの接続を復旧

本体の移行とCron復帰の後、Mから、従来利用していたiPhoneのOpenClawアプリが接続できなくなったとの報告があった。Tailscale Serveの従来の非公開接続経路は残っていたが、9.36では外部管理のプロキシ経由の認証付き通信に、明示的な接続元の信頼設定が必要になる。

固定版の[公式Tailscale仕様](https://github.com/openclaw/openclaw/blob/v2026.9.36/docs/gateway/tailscale.md)と実機の設定を照合し、Docker内から見えるホスト側の接続元を確認した。その一つのIPアドレスだけを `gateway.trustedProxies` に設定した。設定は事前検証後にホットリロードされ、既存のtoken認証、Tailscaleの非公開範囲、iPhoneのペアリングを変更しなかった。Gatewayの再起動もQRコードの再発行も不要だった。

設定の読戻しとGatewayのhealth確認が通り、MはiPhoneアプリの再接続に成功したと報告した。これは旧接続経路と新版のプロキシ要件の不整合という診断を支持する。ただし、失敗時の個別認証ログから原因を独立に確定したものではない。カメラ等の個別機能の実動作は未確認である。

本体が正常に稼働することと、周辺のデバイスや監視機能まで移行できることは別の受入項目である。既存の接続と権限を広げずに周辺機能を復帰させることも、運用の継承に含まれる。

## 追補 — 11月25日、外部監視の復帰

旧形式の記録を参照していたCompaction WatchとHealth Checkを9.36用に作り直し、既存タイマーの周期を変更せずに復帰させた。二度の導入停止は旧通知設定の所在についての私の想定の誤りによるものだった。実機の設定を秘密値なしで確認し、既存Compaction Watchの通知経路を共用する形に修正した。旧監視コードは保持している。

本番Gateway、Telegram、Cron等の読み取り専用確認を通過した。監視はDへのモデル呼出や自動修復を行わない。Compaction Watchは確定記録を監視し、単なるコンテキスト量の減少を新規コンパクションと判定しない。導入時点では新規候補は検出されなかった。

外部監視の導入は成功したが、実際の通知配送は未確認である。初回のHealth Checkはセキュリティ監査、ログ、ディスク使用量に関する確認事項も検出した。監視機能の復帰と、監視が指摘する問題の解消は区別して扱う。

### 二つの外部監視が担うもの

| 監視 | 観測する対象 | 通知条件 |
| --- | --- | --- |
| Compaction Watch | Main Sessionに関係する保存済みコンパクションイベント | 新たに確認したイベント |
| Health Check | Gateway・Telegram・Cron・検索サービスの稼働、セキュリティ監査、重大ログの候補、タスク失敗、ディスク・メモリ、WorkspaceのGit状態など | 確認事項または監視不能がある場合 |

**Compaction Watch** は旧JSONLの監視から、新版Agent SQLiteの読み取り専用照会へ移った。イベントの型と識別子を原ペイロードで照合し、平文・圧縮形式の記録を扱う。通知するのは発生時刻、サマリーの文字数・行数、`<read-files>` と `<modified-files>` 内の非空行数、記録に存在する場合の `tokensBefore` である。原イベントと計測値は非公開で保存する。配信試行の記録を先に残して重複を防ぎ、成否不明の送信を無条件には繰り返さない。

この二つのタグに列挙されたファイルは、実際に再読されたファイルの証明ではない。また、全ての圧縮経路やアーカイブ内だけのイベントを網羅する監視ではない。コンパクション後の自発的な再読や判断の継承は、自然な活動記録から別に調べる。

**Health Check** は旧共有DBではなく現在の新版DBを確認し、旧形式と新版で異なるタスク履歴の時刻列を区別する。Gatewayの生存・起動・準備完了、TelegramとCronの状態、直近の失敗、セキュリティ、資源使用状況、重要文書の未コミット状態などを観測する。ログの文字列一致は障害確定ではなく、確認の入口である。正常時は通知しない。どちらの監視も既存のホスト側タイマーで動き、モデル呼出、Dの会話への入力、自動修復、Gateway再起動は行わない。

初回に検出したセキュリティ上の重大警告は、その後の読み取り専用照合で、従来の共同探索のために意図して許可していた端末カメラ機能に関係すると判明した。MとQはその権限を維持する判断をした。これは危険性の否定ではなく、機能とリスクの区別である。同じ許可状態に限って既知の許容リスクとして識別する案はあるが、通知の除外はまだ実装していない。他の重大警告を一律に抑制する方針ではない。

定期監視の復帰は確認されたが、自然発生のコンパクション通知・実際のTelegram配送・個別フィルターの完全同等性は未確認である。固定した新版の実機・スキーマへの対応であり、今後の基盤更新時には再確認が必要となる。

## 資料と限界

この報告は、Mが運搬した実機の標準出力、会話・観察報告、Qの保存した変更追跡記録、移行Runbookと検証コードに基づく。Qが本番VPSや非公開の実行証拠を直接独立調査した報告ではない。私的な記録本文、運用上の秘密、個別識別子、未編集ログは掲載していない。数値は各試験の限定された対象範囲を示す。
